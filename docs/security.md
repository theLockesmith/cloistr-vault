# Security Model

## Zero-Knowledge Architecture

Coldforge Vault implements a **zero-knowledge architecture** where the server never has access to your unencrypted data. This means:

- ✅ **All encryption/decryption happens on your device**
- ✅ **Server only stores encrypted blobs**
- ✅ **Your master key never leaves your device**
- ✅ **Even if servers are compromised, your data remains secure**
- ✅ **We cannot decrypt your data even if legally compelled**

## Encryption Details

### Client-Side Encryption (vault format v2)

The vault uses **envelope encryption**. A random 256-bit **data encryption key
(DEK)** encrypts the vault body and never changes. Each enrolled unlock factor
derives a **key encryption key (KEK)** that wraps its own copy of the DEK.

- **Body**: AES-256-GCM under the DEK
- **Password KEK**: Scrypt with N=32768, r=8, p=1
- **Passkey KEK**: HKDF-SHA256 over the WebAuthn PRF output (no stretching — the
  PRF result is already uniformly random)
- **Wraps**: AES-256-GCM, one per factor
- **Salt**: 32-byte random salt per wrap
- **Nonce**: 12-byte random nonce per encryption operation
- **AAD**: each ciphertext is bound to its role, so a wrap cannot be replayed as
  the body and a password wrap cannot be presented as a passkey wrap

Consequences of the split: adding or removing an unlock factor rewrites only a
wrap, never the body; saving the vault rewrites only the body, so a save does
not re-run scrypt; and a passkey can unlock the vault without the master
password ever being involved.

Implementation: `frontend/web/src/crypto/` (`envelope.ts`, `vault.ts`,
`prf.ts`).

### Vault format v1 (deprecated, read-only)

Vaults written before v2 are in a weaker format that did **not** match what this
document previously described. v1 derived a key with PBKDF2-SHA256 (100,000
iterations) and passed it to CryptoJS as a *passphrase*, which applies OpenSSL's
`EVP_BytesToKey` — a single round of MD5 — and encrypts with **AES-256-CBC**.
v1 vault data is therefore **unauthenticated**: tampering with a stored blob
cannot be detected.

v1 vaults are migrated automatically. The first unlock with the master password
decrypts through the legacy reader, re-keys the vault into a v2 envelope, and
writes it back. The original blob is left intact until the rewrite succeeds, so
an interrupted migration loses nothing and simply retries. There is no v1
writer: `frontend/web/src/crypto/legacy.ts` is decrypt-only and can be deleted
once no v1 vault remains.

### Password Generation
- **Source**: `crypto.getRandomValues` (CSPRNG)
- **Selection**: rejection sampling, so no character is favoured by modulo bias
- **Shuffle**: Fisher-Yates driven by the same CSPRNG

Passwords generated by builds before this change drew from `Math.random()`, a
non-cryptographic PRNG whose internal state is recoverable from its output.
**Any password generated by an older build should be rotated.**

### Password Hashing
- **Algorithm**: Scrypt followed by SHA-256
- **Parameters**: N=32768, r=8, p=1 (configurable)
- **Salt**: 32-byte random salt per password
- **Storage**: Only the hash is stored, never the plaintext

### Nostr Integration
- **Key Format**: secp256k1 private keys (32 bytes)
- **Signatures**: ECDSA with SHA-256 hashing
- **Challenge**: 32-byte random challenge for each auth attempt
- **Key Derivation**: Scrypt using private key as input

## Authentication Methods

### 1. Email/Password Authentication

**Registration Flow:**
```
1. User provides email + password
2. Client generates a random DEK and a random scrypt salt
3. Client derives KEK: scrypt(password, salt)
4. Client encrypts the vault body with the DEK
5. Client wraps the DEK under the KEK
6. Client hashes password: sha256(scrypt(password, salt))
7. Server stores: email, salt, password_hash, encrypted_vault (envelope)
```

**Unlock Flow:**
```
1. Server returns the stored envelope
2. Client derives KEK: scrypt(password, wrap.salt)
3. Client unwraps the DEK from the password wrap
4. Client decrypts the vault body with the DEK
```

### 1a. Passkey Vault Unlock (WebAuthn PRF)

Distinct from passkey *login*, which proves identity to the server and returns a
session token but no key material.

**Enrolment (requires an unlocked vault):**
```
1. Client generates a random PRF salt
2. Authenticator evaluates PRF(credential_secret, salt) -> 32 bytes
3. Client derives KEK: HKDF-SHA256(prf_output)
4. Client wraps the existing DEK under that KEK and appends the wrap
5. Body is untouched; the password wrap is untouched
```

**Unlock:**
```
1. Client reads credential IDs + PRF salts from the envelope (no key needed)
2. Authenticator evaluates the PRF for the chosen credential
3. Client derives the KEK and unwraps the DEK
4. Client decrypts the vault body
```

The master password wrap always remains, so losing or replacing an
authenticator never makes a vault unrecoverable. Authenticators without
CTAP2 `hmac-secret` cannot unlock the vault and are reported as such.

### 2. Nostr Authentication

**Registration Flow:**
```
1. User provides nostr public key
2. Client derives vault key: scrypt(private_key, salt)
3. Client encrypts vault with derived key
4. Server stores: nostr_pubkey, encrypted_vault
```

**Login Flow:**
```
1. User provides nostr public key
2. Server generates random challenge
3. Client signs challenge with private key
4. Server verifies signature
5. If valid, server returns encrypted vault
6. Client derives key and decrypts vault
```

## Recovery Mechanisms

### Recovery Codes
- Generated during account creation
- 8 recovery codes in format: `xxxx-yyyy-zzzz`
- Each code can only be used once
- Hashed and salted before storage
- Can be used to reset password or recover account

### Trusted Device Recovery
- Devices can be marked as "trusted"
- Trusted devices can authorize new device access
- Uses public key cryptography for device authentication
- Time-locked recovery process for additional security

## Threat Model

### Protected Against:
- ✅ **Server compromise** - encrypted data remains secure
- ✅ **Database breach** - only encrypted data and hashes stored
- ✅ **Man-in-the-middle attacks** - TLS + client-side encryption
- ✅ **Timing attacks** - constant-time comparisons
- ✅ **Rainbow table attacks** - salted and stretched passwords
- ✅ **Legal data requests** - we cannot decrypt user data

### Considerations:
- ⚠️ **Client-side malware** - could capture master password
- ⚠️ **Phishing attacks** - users must verify authentic domains
- ⚠️ **Lost master password** - no recovery without recovery codes
- ⚠️ **Compromised client device** - local data may be accessible

## Best Practices

### For Users:
1. **Use a strong, unique master password**
2. **Store recovery codes in a safe location**
3. **Enable two-factor authentication when available**
4. **Keep client applications updated**
5. **Use trusted devices for sensitive operations**

### For Deployment:
1. **Use HTTPS everywhere** - no exceptions
2. **Configure proper TLS certificates**
3. **Enable database encryption at rest**
4. **Implement proper network security**
5. **Regular security updates and patches**
6. **Monitor for suspicious activity**
